1. Testing methodology
What the server is and what we test. Three MCP servers (FastMCP on Databricks Apps), 14 tools total — six read tools (nih-grants-outputs), three inference tools (nitrd-classifier), and five tools on the gated reviewer-portal server — are served over stdio and streamable HTTP. Only review-request submission and decision recording mutate sandbox records. The workflow shortlists NITRD-relevant awards for SME review, suggests a program component area (PCA), and supports an SME-reviewed fingerprint refresh. The human remains the decision-maker; the server is an assist, never an official classification. The deployed parent classifier nitrd-parent-v2 (§2.1) and the Task 1 evaluation fingerprint task1-fingerprint-v1 (§2.2–2.4) are distinct models and evaluation populations.

Three evaluation endpoints, kept distinct (following the automation-bias literature; see §2): (a) independent SME–SME reliability — not measurable from public data (no dual-reviewed public records); (b) model performance against the official RCDC NITRD listing as reference — what we measure; (c) model-assisted reviewer performance — future work, because showing a reviewer a recommendation changes their decision (automation bias) and assisted agreement cannot stand in for independent reliability.
Held-out discipline. The Task 1 fingerprint is built only from FY2021 text and labels (FY2019–2020 text stabilizes the vocabulary; no FY2019–2020 labels are used). The analysis plan, scoring rule, universe definition, and metrics are pre-registered with a timestamp and SHA-256 and witnessed in a separate append-only repository before any sealed key is read. The cited screening/classification summaries span κ 0.56–0.82: Mateen’s title/abstract screening, Neves’ first annotation round, and Hanegraaf’s mean across 12 abstract-screening studies. This is a range of contextual estimates, not a confidence interval, exhaustive literature range or NITRD-specific standard. Model-vs-listing κ 0.42 is below each. Human-vs-human agreement is a different estimand; no human-parity claim follows from this comparison.

2.6 Explicitly not measured
Not measured here: latency/throughput/concurrency/cost per review beyond the parity latency readout; reviewer time saved; incumbent analyst-screen yield; assisted-review accuracy or reliability; resistance to hostile metadata, data exfiltration and approval bypass; independent human-labeled PCA agreement; and autonomous tool-selection success. The deployed evidence is scripted tool chains. Agent-level tool-selection and adversarial evaluation remain [Planned]; neither a committed tool schema nor a successful fixed chain establishes agent performance.
Failure behavior. [Repo-reported] The inspected src/shared/sql.py implements one bounded deadline covering submission, polling and result retrieval, sanitized errors, and a distinction between definite failure and an unknown write outcome. Unknown writes instruct the caller to read back before retrying. tests/test_sql_failures.py contains simulated transport, timeout, authentication and sanitization cases. These code/test observations are not independently rerun deployment evidence. Live fault injection for SQL timeouts, upstream unavailability, partial writes and concurrent retries remains unmeasured in this evaluation. The 41-award run is a functional scale exercise, not a load or concurrency benchmark.

3. Security considerations
Separation by side effect. Read, inference, and write live in three servers, so an MCP host can grant the read and inference servers freely and gate the only writing server on user confirmation — a per-server trust decision hosts already support.
Sandbox enforced in the table, not just the code. Unity Catalog CHECK constraints reject any review row lacking sandbox=true and the demonstration label, whatever the code does. There is no delete tool; cleanup is an owner or end-to-end runner action. [Repo-reported] The portal App service principal holds MODIFY on the sandbox tables, so deletion is excluded by the tool surface, not by database grants. A principal with MODIFY can change the audit tables: the trail is not tamper-evident. [Planned] Move cleanup to a separate principal and restrict the serving App accordingly; that separation is not yet implemented or tested. The servers never write to IMPAC II or RCDC.
Source: Current architecture and grant caveats; security controls and cleanup plan.
Reserved-year guard. Cohort and operator surfaces refuse FY2022–2026 before SQL (require_build_fy()), keeping those builder-facing surfaces from reserved-year labels. This surface-specific guard does not cover the fixed end-to-end demo chain: its pre-guardrail FY2022 fixtures use the pre-existing per-project tools by appl_id and per-category discovery, not outputs_find_cohort or the operator pages. Those historical fixtures remain FY2022. The current operator-page cards instead use the FY2019 selections documented in §1, and their cohort/operator path remains guarded. The guard constrains this build; it cannot retract FY2022/FY2023 public exposure or File A exposure. The pre-registration’s exposure ledger and the tier-specific reporting carry those qualifications.
Sources: Guard scope and pre-guardrail fixture note; demo fixture years and application IDs; fixed chain and its tool calls.
Governed write semantics. Submissions carry a durable request_id and an idempotency_key: the same key with an identical payload returns the existing record; the same key with a changed payload is a conflict, never a silent update. Decisions are final; a second decision is refused. Every submit, route, and decision writes an audit event recording the persona acted-as and the signed-in workspace user.
Identity is not authentication. Personas are chosen, not proven; the system is a demonstration, not an access-control boundary. Stated plainly so no reviewer over-reads the persona model.
Public-data scope and hygiene. [Repo-reported] The 2026-11-03 sweep reported no credentials in current files or inspected git history; exported run evidence is scanned and workspace identifiers replaced with placeholders. This is a scoped scan report, not a guarantee that no secret can exist. The current demonstration uses public award/publication data. Untrusted text. Award abstracts and publication metadata can carry injection attempts; the agent should treat them as data, never as authority to change a reviewer, approve a write, or disclose credentials. Resistance is not yet measured at agent level — a planned item (see §4), and a focus of the Harness 11-12 governance lab (prompt injection, data leakage, policy-gated release).
Implemented in this prototype. Reviewer-tier checks operate over chosen, unauthenticated personas; Unity Catalog CHECK constraints enforce the sandbox independently of application code; reserved-year guards constrain builder-facing queries; idempotency keys reject changed-payload conflicts; decisions are final; audit events distinguish the persona acted-as from the signed-in workspace user. The write surface is narrow: submit requests and record decisions, with no delete tool, arbitrary SQL or URL fetch. These are deterministic execution constraints, not authenticated user authorization or demonstrated prompt-injection resistance.
Production design, not implemented or tested here. Authenticated end-user authorization; approval cryptographically bound to the exact actor and call; demonstrated resistance to prompt injection and approval bypass; runtime attack monitoring; and a separate cleanup principal with an audit trail protected from modification. Untrusted scientific text must be treated as data. Avoiding writes to official systems limits impact; it does not establish zero leakage of queries, caller identity or credentials.
Adversarial evaluation [Planned]. Server and agent need separate tests. The planned agent suite will adapt AgentDojo (Debenedetti et al., NeurIPS 2024 Datasets & Benchmarks track; arXiv:2406.13352: 97 tasks and 629 security test cases) and InjecAgent (Zhan et al., Findings of ACL 2024, pp.10471–10506; 10.18653/v1/2024.findings-acl.624: 1,054 indirect-injection cases over 17 user tools and 62 attacker tools). These are benchmark designs to adapt, not this server’s test counts or success rates. No injection-resistance, approval-bypass or data-exfiltration result has been measured here.

4. Lessons learned and recommendations
The pivot that defined the project. The first build subcategorized pre-shortlisted projects and scored 24/214 against a held-out key — an honest number, but it measured the wrong task. The real NITRD workflow screens all NIH awards to produce a shortlist for SMEs, identifies the PCA, and refreshes the fingerprint that seeds next year. We rebuilt around that three-task workflow with a human in the loop. Lesson: model the actual decision process before optimizing a metric.
The reframe that made the evaluation honest. The official listing is the available reference, not an independently adjudicated truth set. The FY2024 Tier 2 (non-File-A) result supports high-recall triage: 0.93 recall at an overall shortlist budget of ~12%, with κ 0.42 below the contextual screening/classification estimates spanning 0.56–0.82. The budget is relative to the full filtered universe, not a measured saving over current analyst practice. Recommendation: report recall-at-burden as the headline and model-vs-listing agreement as context; never present it as human inter-rater reliability. These are different estimands, and independent human reliability is not computable from the available public NITRD labels.
Drift is real and only partly attributable. The PCA history over FY2016–2026 includes documented FY2017–2018 restructuring, AI added FY2020, ENIT electronics added FY2022, and LSN networking renamed ACNS in FY2023. NITRD’s official year-specific PCA definitions and change histories document these changes. They do not establish a sharp pre-FY2019 statistical regime break or attribute the observed classifier decay to taxonomy changes alone. We can measure net performance decay of a frozen fingerprint across years; we cannot cleanly separate fingerprint drift from program-emphasis drift from reported-spending drift without the internal instruments. Recommendation: treat the fingerprint like RCDC disease categories — a living artifact with an annual, SME-reviewed refresh (Task 3), never an autonomous rewrite.
Sources: FY2017 PCA changes; FY2018 PCA changes; FY2020 AI addition; FY2022 definitions; FY2023 changes, including ENIT’s FY2022 introduction. These are NITRD’s official definitions associated with each annual Budget Supplement; the PDF supplements were not independently retrieved in this revision.
Evaluation integrity without environment access. Public commits and the hash-and-witness chain allow judges to verify artifact integrity and ordering—that predictions and the analysis plan were committed and hashed before the key was opened. They cannot establish absence of prior human exposure; the exposure ledger records that limitation. The pairing of a governed sandbox write workflow with inspectable evidence is the proposed reusable agency pattern.
Recommendations for production. Complete agent-level tool-selection and injection evaluation; add a release policy gate, authenticated authorization and runtime attack monitoring; validate approval binding and live failure/concurrency behavior; and formalize annual SME-reviewed fingerprint refresh. Read/write tool annotations and SQL failure handling exist in the inspected commit; their presence must not be described as proof of agent safety or live fault tolerance. Faster reporting and improved consistency remain intended mission benefits until reviewer time and assisted-review outcomes are measured.
Operational verification outstanding. Identify the executing principal and invocation path for Arm C from run or audit metadata; compare the separate agent 403’s exact endpoint, principal, timestamp, request ID and authorization outcome before diagnosing permissions or model availability. The committed Arm C endpoint was Llama 4 Maverick, not gpt-6-astra. Obtain the GitHub Support ticket and closure confirmation for cached-object removal; the witness reports filing, not completion. These checks require deployment or support evidence unavailable to a repository-only judge.

## Paragraph

At the time of evaluation, the reviewer portal enforced ordering and single-decision semantics but not who decides. Lifecycle run d74756ca showed the portal's service principal moving a request from pending (Delta v298) to approved (v299) with no human action. Fix (c) adds an identity control. A decision is accepted only when the x-forwarded-email header, which the Databricks Apps proxy sets from the caller's authenticated identity, matches an entry on an explicit approver list (case-insensitive, whitespace-trimmed). An empty or missing list refuses every decision.

Before relying on the header, we tested its integrity. A request carrying x-forwarded-email set to a spoofed address reached the app with the signed-in user's real address, so the proxy overwrites client-supplied identity headers. That test ran on a human sign-in only; that the same holds for service principals is an inference, not a measurement. A pattern match on "@" would not work: x-forwarded-user is `<id>@<workspace>` for people and service principals alike, and for a service principal x-forwarded-email carries its application id.

The deployed MCP tool path has no human positive control, because no person can call the decision tool over /mcp in our test harness. What stands in for it is the refusal reason the portal logs: a service principal's refused decision must log `not_in_set` with that principal's id, which shows the header reached the tool. A refusal logged as `absent` would mean the control refuses everything without ever seeing an identity, and it would not count as a pass. In general, a control that refuses every request passes every negative test, so a negative suite alone cannot establish that a control works. That is why the logged reason, not the suite result, is the evidence here. A person deciding is shown on the deployed portal only through its review page, which runs the same check.

Since commit d7bad89, the deployed portal refuses decisions from identities not on the approver list. In lifecycle run 3174122a, all four decisions submitted by the runner's service principal over the MCP tool were refused. For each one, the portal log records `not_in_set` with that principal's id. A listed person can still decide, as before the fix. On 2026-11-09 the owner's decision on the review page of the same deployment was accepted and recorded under the assigned persona. The owner's sign-in appears only in the portal's action log. The fix did not create the ability for a person to decide: the owner had decided through the same page on 2026-11-08, before any approver check existed. What the fix removed is every other identity's ability to decide.

[Proposed addition, who can exercise the decision path; not approved. Rewritten 2026-11-09 so the consequence of the design leads and the gap follows: "The control permits only a person on the approver list to decide, so on the deployed system only a person can exercise the decision rules. That is the point of the control, not a side effect. Our automated runner is not on the list and must not be, so every automated deployed call of the decision tool stops at the approver check. We therefore exercise the rules behind it by hand. A listed person records an override with its corrections, and we confirm that the decision and both corrections are stored. The same person then tries a second decision on that request and a decision under a persona the request is not assigned to; both must be refused. The remaining rules stay covered by the offline test suite only: the minimum rationale, the three rules on override corrections, and queue and history ordering. Testing them automatically on the deployed system would mean putting the runner on the approver list, which is exactly the ability the control removed."

## Paragraph

At the time of evaluation, the reviewer portal enforced ordering and single-decision semantics but not who decides. Lifecycle run d74756ca showed the portal's service principal moving a request from pending (Delta v298) to approved (v299) with no human action. Fix (c) adds an identity control. A decision is accepted only when the x-forwarded-email header, which the Databricks Apps proxy sets from the caller's authenticated identity, matches an entry on an explicit approver list (case-insensitive, whitespace-trimmed). An empty or missing list refuses every decision.

Before relying on the header, we tested its integrity. A request carrying x-forwarded-email set to a spoofed address reached the app with the signed-in user's real address, so the proxy overwrites client-supplied identity headers. That test ran on a human sign-in only; that the same holds for service principals is an inference, not a measurement. A pattern match on "@" would not work: x-forwarded-user is `<id>@<workspace>` for people and service principals alike, and for a service principal x-forwarded-email carries its application id.

The deployed MCP tool path has no human positive control, because no person can call the decision tool over /mcp in our test harness. What stands in for it is the refusal reason the portal logs: a service principal's refused decision must log `not_in_set` with that principal's id, which shows the header reached the tool. A refusal logged as `absent` would mean the control refuses everything without ever seeing an identity, and it would not count as a pass. In general, a control that refuses every request passes every negative test, so a negative suite alone cannot establish that a control works. That is why the logged reason, not the suite result, is the evidence here. A person deciding is shown on the deployed portal only through its review page, which runs the same check.

Since commit d7bad89, the deployed portal refuses decisions from identities not on the approver list. In lifecycle run 3174122a, all four decisions submitted by the runner's service principal over the MCP tool were refused. For each one, the portal log records `not_in_set` with that principal's id. A listed person can still decide, as before the fix, and the rules behind the approver check still hold for that person.

On 2026-11-09 the owner, a listed approver, had two review decisions and one draft authorisation accepted on the deployed build:
* On the review page, an approval was accepted and recorded under the assigned persona.
* In the agent app, an agent draft was authorised, which created one pending request.
* On the review page, an override was accepted. Both corrections, the parent label and the corrected list of program component areas, were stored and carried in the audit event.

On the same deployment, a second decision on the overridden request was refused as final. So was a decision submitted after the page's hidden persona field had been edited by hand to a persona the request was not assigned to. The portal's log shows the edited value arrived, so the server, not the page, refused it. None of these refusals came from the approver check, and none wrote anything. The owner's sign-in appears only in the portal's action log. The fix did not create the ability for a person to decide: the owner had decided through the same page on 2026-11-08, before any approver check existed. What the fix removed is every other identity's ability to decide.

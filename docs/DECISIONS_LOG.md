## 2026-11-01 Step G decisions (G.4.3 Path B: scan findings)

- **2026-11-01: Path B refactor on scan findings (corrected).** The scan on outputs deployment `01f1d655…` (commit 7c08ba7) returned 4 Critical SQL-injection findings on `src/nih_grants_outputs/data.py` lines 287-293. The initial identification was wrong: they were thought to be in `prior_year_sql`, but inspection showed they are in `fetch_publications`'s two MeSH / pub-type lookups, which built `WHERE pmid IN ({ids})` by inlining PMIDs into SQL text via `_pmid_list` (not parameter-bound; code from c554a16d, 2026-10-27, deployed since Gate 4 when no scan ran).
  - These are real pattern findings, not false positives. The specific exploit path is closed (the PMIDs come from our own earlier query, cast to int, not from user input), but SQL text built from an inlined value sequence is pattern-identical to classic SQL injection. A later change that made the PMIDs user-supplied would turn it into a live vulnerability without the scanner getting another chance to flag it. The scanner was right to flag.
  - `prior_year_sql` built `:core_<i>` placeholder names with an f-string but bound the values, which is why it was not flagged. Structurally different, but refactored too (Scope B): it ships in the portal (submission flow, via shared/prior_year.py), and the portal's first scan at G.4.6 would otherwise flag the related pattern after the migrations had already run.
  - Both now use fixed SQL with one bound JSON parameter: `array_contains(from_json(:pmids, 'ARRAY<BIGINT>'), pmid)` and `array_contains(from_json(:cores, 'ARRAY<STRING>'), core_project_num)`. The Statement Execution API rejects ARRAY parameter types (INVALID_PARAMETER_MARKER_VALUE.INVALID_DATA_TYPE), and a bare STRING is not an array, so `from_json` over a JSON-string parameter is the working form (read-only probe; a list holding `x') OR 1=1 --` stays data).
  - `json_array_param(items, name, item_type)` in shared/sql.py builds the parameter and raises ValueError before any SQL: not a list (str/bytes/dict/set), None items, wrong item type (bool is not int), NaN/infinity, not JSON-serializable. Both call sites use it.
  - Behavior preserved: old (7c08ba7) vs new byte-identical on the live warehouse for publications (37 FY2021 NIBIB U01 cores + 5 demo cores) and prior years (37 cores; also equal to an independent PySpark count: 87 core-years, 99 records, 35 continuing / 2 new / 8 ever-NITRD). The offline fakes now read the bound parameter and refuse the old patterns; two new live tests compare the lookups with a plain join / per-core query (the fake does not execute SQL, so a predicate that silently matches nothing is caught only live). Test assertions that encoded the old SQL shape (3) were updated; behavior tests unchanged.
  - Precedent: dynamic SQL uses bound array parameters via `from_json` (through `json_array_param`), not inlined values or generated placeholder lists. Remaining f-string SQL in src/: constant-only interpolation (table names, column lists), plus `cohort_events`' fixed subquery string and the catalog name from the SCHEMA constant.
- **2026-11-01: `from_json` silent behaviors (reference for future array-param use).** `from_json(:p, 'ARRAY<...>')` handles bad input silently (no error) in several distinct ways:
  - Trailing content after valid JSON is ignored (`'[1,2]]'` parses as `[1,2]`); cannot be reached through `json.dumps`.
  - One wrong-typed item: nulls the whole array for `ARRAY<BIGINT>` (`'[1,"2"]'` gives NULL); is coerced to a string and silently matches nothing for `ARRAY<STRING>` (`'[1,"R01..."]'` gives `["1","R01..."]`; booleans and objects likewise).
  - NaN or a non-integer in an integer array nulls the whole array; prevented by `allow_nan=False` + strict `item_type`.
  - `null` in an array is preserved; prevented by the None-item check.
  - `json_array_param` guards against all of these by rejecting on the Python side before SQL. Future array-param uses: go through `json_array_param` or write equivalent guards. (In prior_year_nitrd the helper is a backstop: the cores are already normalized to non-empty upper-case strings, so bypassing it changes nothing a test can see.)

## Troubleshooting

- **Kernel filesystem cache vs. workspace API writes:** if the shell, git, or Python `os.listdir` cannot see a file that the workspace API shows exists as a normal FILE, suspect the kernel's filesystem cache holding a negative lookup from a prior deletion of the same path. This happens when a file is deleted (e.g. by `git clean`) and recreated at the same path via the workspace API in the same session. Fix: detach and re-attach the notebook, or terminate the compute. Programmatic compute-switch does not reset the kernel. Confirm by checking the host and cluster ID changed. Files created at new paths (never deleted first) are unaffected. (2026-10-30: `src/shared/ics.py` and `src/nih_grants_outputs/tools/find_cohort.py`; fixed by terminating the session in the UI. - **Editor stale-write rejections that actually landed:** when `Edit Asset` reports an edit as rejected (often during parallel edits or quick sequential writes to the same file), verify the file state before retrying. The edit may have been saved despite the error, in which case a retry duplicates the content (observed 2026-10-30: a test function was duplicated in `tests/test_portal_classification.py`; one copy had to be removed afterward). Confirm by reading the file through both the workspace API and the shell before issuing a retry. Pair with the kernel-cache gotcha above: if the shell view disagrees with the workspace API, suspect that cache first.
